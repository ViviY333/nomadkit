# Nomad Kit MVP 2.0 产品与工程决策

日期：2026-07-16  
阶段：MVP 2.0 规划  
目标：在 SwiftUI MVP 基础上，明确真实数据、Apple 原生设计规范、保险跳转、签证判断、地图 SDK、Onboarding 的产品边界和开发顺序。

## 1. 总体原则

MVP 2.0 的核心不是一次性接入所有真实服务，而是在保持产品可用性和安全感的前提下，逐步替换 Mock 数据。

优先级：

1. 先原生体验：遵循 Apple Human Interface Guidelines，用 SwiftUI + SF Symbols + 原生导航/表单/Tab 体系。
2. 先本地可用：v0.1/v1 仍以本地 JSON、Mock Service、手动输入为主。
3. 后接真实数据：天气、汇率、地图可以逐步接；签证、保险、医疗信息必须谨慎。
4. 先信息聚合，不做交易闭环：保险/eSIM/签证服务先做第三方跳转，不在 App 内完成购买或办理。
5. 先用户确认，再自动识别：签证、护照、保险等敏感信息先手动输入，OCR/照片识别后置。

## 2. 信息架构与核心页面

### 2.1 Tab 结构

MVP 的主导航收敛为两个 Tab：`今日` 与 `清单`。

- `今日`：回答“我今天在这座城市怎么安排”。
- `清单`：回答“我是否已经为旅居做好准备”，并承载城市打卡与护照记录。
- 不再保留独立的 `打卡` Tab，避免将一次性记录行为与日常行动入口并列。

### 2.2 清单：从完成率改为确认感

清单不是强制待办。用户可能已具备某项资源，也可能按旅居方式不需要某项。因此禁止使用以下表现：

- 整体进度条和百分比。
- 分类进度条。
- 暗示必须完成全部条目的“已完成 X/Y”主状态。

改为“安全感指数”状态卡：

- 用户主动勾选“已确认”的事项。
- 分类入口仅显示 `待确认`、`已确认` 或 `已确认 N 项`。
- 指数用于反馈用户已确认的准备覆盖度；不把未勾选事项视为失败，也不等同于城市客观宜居评分。
- 类别详情是可勾选的 To-do 列表，保留筛选，但不出现进度条。

清单页顶部分段：

1. `清单`：安全感状态卡与准备分类。
2. `打卡`：城市印记、旅居记录、徽章与护照分享。

### 2.3 今日：一张城市状态卡

今日页不再拆分天气、气温、城市评分与本地渠道为多个大模块。核心是一张可切换正反面的城市状态卡：

- 正面：当前城市、今日状态分、总体判断、天气与气温。
- 背面：工作、预算、社交等城市维度。
- 点击卡片切换；同时提供清晰的辅助文案，不能只依赖隐藏手势。

今日页只保留三类内容：

1. 城市状态卡。
2. 精选地点地图。
3. 今日提醒。

“本地渠道”从今日页移除，相关联网、现金、交通、药店等信息归入清单分类详情。

### 2.4 精选地点地图

地图是一个局部的城市行动入口，不是独立地图产品。

- 在今日页展示一张 MapKit 小地图。
- 只标记人工精选的数字游民常去地点：coworking、办公咖啡馆和活动场所。
- MVP 使用本地 Mock 点位；不请求用户位置，不做路线规划、实时追踪或社交位置共享。
- 后续可扩展至 Apple Maps 跳转、收藏和人工验证，但不在本阶段做附近搜索或用户投稿。

## 3. 真实数据接口规划

### 2.1 数据接入优先级

| 数据类型 | MVP 2.0 建议 | 后续接口候选 | 风险 | 备注 |
|---|---|---|---|---|
| 天气 | 优先接真实数据 | Apple WeatherKit / Open-Meteo | 中 | WeatherKit 更贴近 iOS 原生；Open-Meteo 更轻量 |
| AQI 空气质量 | 可后置或半真实 | OpenAQ / Open-Meteo Air Quality | 中 | 覆盖城市不稳定，UI 必须允许无数据状态 |
| 汇率 | 可较早接入 | ExchangeRate-API / Open Exchange Rates / exchangerate.host | 低-中 | 只做信息展示，不做金融建议 |
| 地点 / 地图 | v2 可轻量接 MapKit | MapKit / Apple Maps Server API | 中 | 先显示精选地点，后做搜索和附近推荐 |
| 签证 / 入境要求 | 不建议早期自动判断 | Sherpa API / 官方使领馆 / 移民局链接 | 高 | 先手动输入 + 官方链接 + 免责声明 |
| 保险 / eSIM 渠道 | 人工维护 + 第三方跳转 | 联盟链接 / 官方购买页 / deeplink | 中 | 不在 App 内购买，不做推荐结论 |
| 翻译 | 可作为后续工具 | Apple Translate 不一定开放完整 API；可考虑系统分享/第三方 | 中 | 不放 MVP 2.0 核心，先作为用户偏好项 |

### 2.2 推荐阶段路线

#### v0.1 / 当前 SwiftUI MVP

- 全部使用 Mock 数据或本地 JSON。
- 所有动态模块预留更新时间字段。
- 所有 Service 用 Protocol 抽象，方便后续替换真实 API。

#### MVP 2.0

优先接入：

1. 天气：WeatherKit 或 Open-Meteo。
2. 汇率：选择一个稳定汇率 API。
3. 地点：MapKit 小地图 + 静态精选地点。

暂不接入：

- 自动签证判断。
- 保险购买 API。
- eSIM 购买 API。
- GPS 自动打卡。
- 医疗/药品建议 API。

#### MVP 3.0+

再考虑：

- Apple Maps Server API。
- Sherpa 等旅行要求 API。
- CloudKit 同步。
- Sign in with Apple。
- OCR 扫描签证/入境章。

## 4. Apple 原生 Design System 决策

### 3.1 结论

MVP 2.0 暂时采用 Apple 官方原生设计规范，不自建复杂组件库。

产品视觉可以保留“城市护照 / 纸感 / 安全感”的品牌气质，但交互、导航、表单、设置、权限、系统组件应尽量贴近 iOS 原生体验。

### 3.2 官方资源

| 资源 | 用途 | 链接 |
|---|---|---|
| Human Interface Guidelines | iOS 产品交互、导航、组件、可访问性原则 | https://developer.apple.com/design/human-interface-guidelines |
| Apple Design Resources | 官方 Figma / Sketch / Photoshop / Keynote 设计资源 | https://developer.apple.com/design/resources/ |
| SF Symbols | Apple 官方系统图标库 | https://developer.apple.com/sf-symbols/ |
| SwiftUI Documentation | SwiftUI 原生组件和布局 | https://developer.apple.com/documentation/swiftui |
| MapKit | iOS 地图能力 | https://developer.apple.com/documentation/mapkit |
| WeatherKit | 天气能力 | https://developer.apple.com/weatherkit/ |

### 3.3 SwiftUI 实现建议

优先使用：

- `TabView`
- `NavigationStack`
- `List`
- `Form`
- `Sheet`
- `Menu`
- `Picker`
- `Toggle`
- `TextField`
- `Button`
- `Label`
- `Image(systemName:)`

设计系统只保留轻量封装：

- `NomadTheme`
- `NomadCard`
- `NomadSectionHeader`
- `NomadIconTile`
- `NomadBadge`
- `NomadPassportBackground`

### 3.4 图标策略

MVP 2.0：

- 信息入口先用 SF Symbols。
- 每个入口可以用卡片 + 系统图标 + 状态文案表达。
- 不因 3D 图标拖慢开发。

后续品牌化：

- 将“保险、eSIM、现金、常用药、工作地点、医院、社群、紧急信息”等入口替换为 3D 小图标。
- 3D 图标作为品牌资产，不影响基础功能。

## 5. 保险购买决策

### 4.1 结论

用户不在 Nomad Kit 内直接购买保险。App 只提供信息聚合、状态记录、到期提醒和第三方跳转。

### 4.2 产品边界

可做：

- 记录用户已购买的保险名称。
- 显示保险到期日、剩余天数、紧急电话。
- 保存理赔材料清单。
- 展示常见保险类型和渠道入口。
- 跳转第三方平台查看或购买。

不做：

- App 内支付。
- App 内销售保险。
- 自动判断保险是否适合用户。
- 对保险覆盖范围做承诺。
- 做“推荐购买某某保险”的强结论。

### 4.3 UI 文案原则

必须出现类似提示：

> 以下信息仅作整理参考，具体保障范围、价格和理赔规则以保险公司条款为准。

状态示例：

- 已购入：`SafetyWing Nomad Insurance · 剩余 9 天`
- 未购入：`你还没有记录保险`
- CTA：`查看常见旅居保险渠道`
- 跳转：`去第三方平台查看`

## 6. 签证判断决策

### 5.1 结论

签证判断必须分阶段做。MVP 2.0 不做自动合法性判断，不上传签证照片，不直接给出法律结论。

推荐路线：

1. 手动输入。
2. 结构化问答。
3. OCR 扫描辅助。
4. 第三方旅行要求 API / 官方链接辅助。

### 5.2 v0.1 / MVP 2.0：手动输入

用户填写：

- 当前国家 / 城市。
- 入境日期。
- 允许停留天数。
- 签证类型：免签 / 旅游签 / 数字游民签 / 学签 / 其他。
- 护照到期日。
- 备注。

App 输出：

- 停留剩余天数。
- 最晚离境日。
- 续签/离境提醒。
- 护照有效期提醒。
- 官方链接入口。

不输出：

- “你一定合法”。
- “你一定可以续签”。
- “你一定可以入境”。

### 5.3 MVP 2.0+：结构化问答

问题示例：

- 你持有什么护照？
- 你现在在哪个国家？
- 你这次入境日期是哪天？
- 入境章 / 签证给了多少天？
- 是否允许续签？
- 是否有多次入境限制？

输出建议：

> 根据你填写的信息，建议在 X 日期前离境或确认续签。请以官方/使领馆/移民局信息为准。

### 5.4 MVP 3.0+：OCR / 拍照识别

可以考虑，但必须谨慎：

- 用 OCR 提取签证或入境章日期。
- 必须让用户二次确认识别结果。
- 优先本地识别，避免上传敏感证件。
- 不默认保存原图。
- 保存前必须用户主动确认。
- 必须有隐私说明。

### 5.5 泰国 DTV 试点

泰国 DTV 作为首个“官方内容二次编辑 + 结构化准备度评估”样本。文章、来源映射、评估问题、判定状态和第一版规则见：

- `prd/visa-thailand-dtv-content-and-assessment.md`

第一版只评估用户是否匹配官方公布的核心场景、还缺哪些材料以及哪些问题需要向受理使领馆确认，不输出批准概率或法律结论。

## 7. 地图 SDK 规划

### 6.1 结论

地图不要一开始做重。Nomad Kit 不是地图 App，地图只是信息入口和地点辅助。

### 6.2 阶段路线

#### v0.1

- 不接地图 SDK。
- 用静态地点列表。
- 距离可 Mock。
- 点击后可跳转 Apple Maps。

#### MVP 2.0

- 使用 MapKit 做轻量小地图。
- 只在地点详情页或城市页局部展示。
- 展示 coworking、咖啡馆、药店、医院、ATM 等精选地点。
- 不做复杂筛选和路线规划。

#### MVP 3.0+

- 考虑 Apple Maps Server API。
- 做城市内地点搜索。
- 根据用户位置推荐附近地点。
- 加用户收藏、已验证、投稿。

### 6.3 地图边界

可做：

- 精选地点。
- 地点详情。
- Apple Maps 跳转。
- 城市内轻量搜索。

不做：

- 重地图首页。
- 复杂路线规划。
- 实时位置追踪。
- 社交位置共享。

## 8. Onboarding 决策

### 7.1 结论

Onboarding 保持简单：三页引导 + 一个首页工具偏好选择。目标不是教育用户，而是了解用户习惯，决定首页模块排序。

不要求登录、不要求定位、不要求上传签证照片。

### 7.2 Onboarding 三页结构

#### 第 1 页：你现在处于哪种状态？

标题：`你现在在哪个阶段？`

选项：

- 准备出发。
- 刚落地。
- 已经在这个城市住了一阵。
- 准备换城市。

用途：

- 判断首页偏“准备清单”还是“今日生活仪表盘”。
- 判断清单页应该优先展示哪些工具状态。

#### 第 2 页：你最想先看到什么？

标题：`首页先放哪些工具？`

让用户选择 3-6 个：

- 签证停留天数。
- 护照到期提醒。
- 当天天气 / 是否下雨。
- AQI 空气质量。
- 汇率。
- 翻译功能。
- eSIM / Wi-Fi。
- 保险状态。
- 现金 / 支付。
- 常用药。
- 今日适合工作还是社交。
- 去哪里安排活动。
- 日记 / 今日瞬间。

用途：

- 生成首页组件排序。
- 作为后续“组件化管理”的默认配置。

#### 第 3 页：你希望它怎么帮你？

标题：`你希望 Nomad Kit 更像什么？`

选项：

- 更安全：提醒签证、保险、紧急信息。
- 更高效：安排工作、汇率、天气、工具。
- 更有生活感：记录城市、打卡、日记、徽章。
- 更社交：活动、本地聚集地、同城游民。

用途：

- 决定首页推荐模块权重。
- 决定日记/打卡/活动是否前置。

### 7.3 Onboarding 后进入 App

进入后：

- 默认进入 `今日`。
- 顶部显示当前城市和第几天。
- 首页模块按用户选择排序。
- `清单`页展示“已开启的工具”和“还没准备的底线”。
- `打卡`页鼓励记录第一条城市瞬间。

### 7.4 Onboarding 避免事项

- 不要一开始问太多证件隐私。
- 不要要求登录。
- 不要强制开启定位。
- 不要要求上传签证照片。
- 不要解释太多功能。
- 不要超过 3 页。

## 9. MVP 2.0 开发优先级

1. SwiftUI 原生 Design System：Apple HIG + SF Symbols + SwiftUI 原生组件。
2. 三页 Onboarding：保存本地偏好，不登录。
3. 首页组件排序逻辑：根据 onboarding 选择生成默认顺序。
4. 清单页：已开启工具状态 + 信息入口。
5. 签证/保险：先手动输入和记录，不做自动判断、不做购买。
6. 天气/汇率：在 Mock Service 稳定后逐步接真实接口。
7. 地图：先静态地点，后 MapKit 小地图。

## 10. 产品边界总表

| 问题 | MVP 2.0 建议边界 |
|---|---|
| 真实数据 | v0.1 全 Mock；MVP 2.0 优先天气/汇率；地图后置；签证最后处理 |
| Design System | Apple HIG + SF Symbols + SwiftUI 原生组件，轻品牌化 |
| 保险 | 信息聚合 + 第三方跳转，不在 App 内购买 |
| 签证 | 手动输入和提醒优先，后结构化问答，再 OCR |
| 地图 | 先静态地点，再 MapKit 小地图，不做重地图 App |
| Onboarding | 三页，核心是收集用户想看的首页工具和使用状态 |
| 翻译功能 | 作为用户偏好项记录，暂不进入核心 MVP |
| 社交 | 打卡和记忆优先，重社交后置 |

## 11. 对 CLAUDE.md 的同步建议

开发 Agent 应遵守：

- 先按 Apple 原生设计规范开发，不追求自研复杂组件库。
- v0.1 / MVP 2.0 的真实数据接口都必须通过 Service Protocol 抽象。
- 签证、保险、医疗、药品信息必须有更新时间和免责声明。
- Onboarding 不要求登录、定位、上传证件。
- 保险只做信息聚合和第三方跳转。
- 地图先轻量 MapKit，不做重地图首页。
